# Abyss 调度器设计

在 mx-llama.cpp（`c4d12e2`）上加三个组件：专家缓存、CED 感知预填充、Engram 异步预取。预计把方案 B 的解码从 16.5 tok/s 提到约 25–35 tok/s，预填充从约 300 tok/s 提到 1,000 tok/s 以上。另外要补上 V4.1 的稀疏索引器，这是一处正确性问题。

数据和结论截至 2026-10-20，硬件和实测见 [CLAUDE.md](../CLAUDE.md)。

## 1. 现状与瓶颈

方案 B（`-sm layer -ts 12/29`，第 22–39 层专家在 CPU 的 `CUDA_Host` 锁页内存里）的实测：

| 指标 | 实测 | 主要瓶颈 |
|---|---|---|
| 解码，空上下文 | 16.5 tok/s | CPU 每 token 读 108 个专家（18 层 × 6），约 2.0 GB |
| 解码，4 万上下文 | 14.6 tok/s | 同上，再加上注意力开销 |
| 预填充，2048 token | 307 tok/s（6.7 s） | CPU 专家约 4.2 s，Engram 随机读约 2.4 s |
| 预填充，1.5–4 万 token | 350–416 tok/s | 同上 |

专家热度统计来自用户自己的智能体负载（预填充 26 万、解码 7 千 token）。解码器层的路由很集中：每层平均 24 个专家就覆盖了一半的解码命中。

**精度和对拍底线**（2026-10-21，`tools/eval/kl.sh`）：

- Blackwell 上 MXFP4 的 MMQ 默认用 W4A4，激活量化到 4 bit，影响所有超过 8 个 token 的批次（预填充）。官方参考实现是 W4A8。设 `GGML_CUDA_MMQ_PREC=q8` 后，预填充路径对解码路径的 KLD 从 0.044 降到 0.012，预填充慢约 5%。表中的预填充速度都是 W4A4 下测的。
- 数值底线分两档。同一配置重跑结果完全相同。
  - 改动只落在解码器层（20–39）时，KLD 约 0.0005。例如把第 22–39 层专家从 CPU 改到 GPU 上算。
  - 改动经过编码器层（0–19）时，0.005–0.01 属正常。例如只把第 5 层专家改到 CPU 算就是 0.0064；换内核、关融合、换 ubatch 也在这个量级。原因是编码器的输出决定了所有位置共享的全局 KV，数值差别会扩散到之后所有位置。
- 下面各阶段的“结果一致”按改动范围判断：只改解码器层时 KLD 不超过 0.001；改到编码器层时平均 KLD 不超过约 0.015，top-1 一致率不低于 95%。

## 2. 总体结构

```
          ┌────────────── GPU0 ──────────────┐   ┌────────────── GPU1 ──────────────────┐
token ──► │ 第 0–11 层（整层）               │ ─► │ 第 12–19 层（整层）                  │
          │ Engram 行（第 1、14 层）◄────┐   │   │ 第 20–39 层稠密部分                  │
          └──────────────────────────────│───┘   │ 专家槽位池（约 1,650 个热专家）  ──┐ │
                                         │       └────────────────────────────────────│─┘
          ┌─────────────── 主机内存 ─────│───────────────────────────────────────────▼──┐
          │ Engram 行缓存（按行，136 B） │   第 20–39 层全部专家（CUDA_Host 锁页）        │
          │       ▲ io_uring 预读        │   CPU 计算未命中的专家，结果和 GPU 的相加      │
          └───────│──────────────────────┴──────────────────────────────────────────────┘
                  │
          NVMe（9100 PRO）：两张 Engram 表，各 48.6 GiB
```

| 组件 | 解决什么 | 预期收益 |
|---|---|---|
| A. 专家缓存 | 解码时 CPU 读专家太多 | CPU 每 token 读的专家从 108 降到 25–45 |
| B. CED 感知预填充 | 提示词每个 token 都跑完 40 层 | 8k 提示词的解码器 MoE 计算少约 7 倍，32k 少约 27 倍 |
| C. Engram 预取 | 缺页同步读、4 KiB 读放大 | 预填充省掉大部分约 2.4 s / 2048 token 的读表时间 |
| D. 稀疏索引器 | 长上下文结果与参考实现不一致 | 正确性；长上下文注意力可能也更快 |

## 3. 组件 A：专家缓存（GPU 命中 + CPU 算未命中）

### 基础

mx-llama.cpp 已有实验性的 `--moe-cache-mib`（`src/llama-moe-cache.{h,cpp}`，接在 `build_moe_ffn` 里）：

- 每个设备有一组专家槽位（bank），每层有一张 `slot_map[384]`，-1 表示未缓存。
- 计算图里用 `get_rows(slot_map, ids)` 把专家号换成槽位号，再对 bank 做 `mul_mat_id`。
- 未命中时同步上传专家，每个约 0.7 ms，大约是 CPU 直接算（约 0.43 ms）的 1.6 倍。
- M1 实测（2026-10-21，14,000 MiB，约 780 个槽位）：4.8 万上下文解码从 14.1 提到 25.2 tok/s，短上下文约 29–30 tok/s，预填充不变，KLD 0.0005。真实文本的专家局部性很强，LRU 命中率高，上传的代价没有预想的大。这个配置已经在 server 上启用。

我们给它加一个“未命中交给 CPU 算”的模式，不另起炉灶。按 30 tok/s 推算，每 token 约 25 次未命中；改由 CPU 算，每 token 约省 7 ms。JigSawPT 的 `--moe-stream` 解决的是从 SSD 流式加载，未命中模型也不同，不移植，只借用它的热度衰减淘汰和固定专家的思路。

### 计算图

只在 `n_tokens < 32` 时启用（解码，以及 B 组件之后的短尾预填充）；更大的批次沿用现有路径，由 GPU 上传用到的专家来算。

在 `build_moe_ffn` 选出专家之后（`llama-graph.cpp:2389` 附近）拆成两路，最后相加：

| 分支 | 专家号 | 权重 | 数据 |
|---|---|---|---|
| GPU | `get_rows(slot_map, ids)`，未命中指向全零的备用槽位 | 门控权重 × 命中掩码 | GPU1 上的 bank |
| CPU | `get_rows(miss_map, ids)`，命中记为 -1 | 门控权重 × 未命中掩码 | `CUDA_Host` 里的原始专家张量 |

- `slot_map` 和 `miss_map` 作为计算图输入，每个 token 传一次，不写死成常量，这样 CUDA graph 和图复用都不受影响。
- **CPU 端补丁（约 10 行）**：`ggml_compute_forward_mul_mat_id` 遇到 id < 0 时跳过，并把对应输出清零（`ggml-cpu.c:1650-1679`，以及 `repack.cpp:4858`）。不打这个补丁的话，6 个专家全命中时 CPU 也得算一个，每层白读 18.8 MB，18 层合计每 token 最多浪费 7.7 ms。
- 输出清零，不靠乘 0 来屏蔽，以免 0 × NaN 产生 NaN。

### 槽位预算

| 位置 | 现在 | 改后 |
|---|---|---|
| GPU0 | 第 0–11 层，运行时 92.3 / 95.6 GiB | 不变 |
| GPU1 | 第 12–21 层专家 + 稠密部分，运行时 79.4 GiB | 第 12–19 层整层；第 20–21 层的 768 个位置和约 16 GiB 空余合并成一个槽位池，约 1,650 个 |
| 主机内存 | 第 22–39 层专家 121 GiB | 第 20–39 层全部专家，约 134 GiB |

主机内存会多占约 13 GiB，Engram 页缓存的可用空间从约 54 GiB 降到约 41 GiB。C 组件改成按行缓存后，这点空间足够。

### 槽位更新

- **热度**：每层每个专家维护一个衰减计数，每生成 N 个 token 乘一个衰减系数。
- **预填充后预热**：同一会话里，提示词的路由能很好地预测解码热度。用整段提示词热度挑专家，在新数据上 CPU 每 token 读 25.8 个专家；用之前的解码热度挑，是 24.7 个（槽位约 1,800 个时）。所以每次预填充结束后，先按本次提示词的路由热度重排一次槽位，再开始解码。
- **更新不进关键路径**：在侧边 CUDA stream 上上传新专家，上传完成后再切换 `slot_map` 里对应的条目。切换之前，这个专家仍由 CPU 计算，结果始终正确。
- **限速**：每个 token 最多换入 K 个专家（初值 4，约占 PCIe 带宽的 10%），避免和 CPU 抢内存带宽。

### 预期收益

用户负载的检验数据（用一份数据挑专家，另一份检验）：

| 解码器层槽位 | 按之前的解码热度挑 | 按新增数据挑，反向检验 | 按预填充热度挑 |
|---|---|---|---|
| 768 | 46.8 | 62.8 | 50.6 |
| 1,200 | 34.6 | 53.2 | 37.5 |
| 1,800 | 24.7 | 43.5 | 25.8 |

表中是 CPU 每 token 要读的专家数，按层切时是 108。按约 1,650 个槽位、每 token 读 25–45 个专家估算，CPU 时间从约 55 ms 降到 13–23 ms，解码约 25–35 tok/s。M1 的现成缓存已经测到 25–30 tok/s，所以组件 A 的增量来自四处：未命中改由 CPU 算，槽位池扩大到约 1,650 个，按热度而不是 LRU 换入，以及预填充后预热。预计在 M1 的基础上再快约 20–30%。这一估算没算 GPU 和 CPU 两路串行执行的开销（每层 GPU 命中部分约 60 µs），也没算更新槽位的开销。

### 实际实现（2026-10-24，`mx-llama.cpp/0009`）

- 先剖析（`tools/eval/profile-decode.sh` + `nsys_decode.py`，4.8 万上下文，M1 缓存，PCIe Gen5）：每 token 40.1 ms。GPU1 上传未命中专家 17.4 ms（每 token 约 26.5 个、474 MiB，28.6 GB/s），GPU1 内核 13.3 ms，GPU0 内核 4.8 ms，两卡都空闲 4.5 ms（每层一次同步，每 token 约 116 次 `cudaStreamSynchronize`），几部分串行。LRU 命中率约 75%。
- 原设计行不通的地方：LRU 的高命中率靠的是每个未命中都换入。未命中全交给 CPU、只按静态热表换入的话，每 token 要读约 47 个专家（上表 768 槽位一行），CPU 算约 21 ms，比上传还慢；CPU 算完再把同一个专家上传，就要从内存读两遍，44 GB/s 的内存带宽先撑不住。
- 改成按热度准入：每层由一个 CPU 算子（`ggml_custom_4d`）规划。命中的照常读缓存；未命中的按衰减热度（每层每步乘 0.99）挑出 `ABYSS_MOE_ADMIT`（默认 0.5）比例，立即异步上传进 LRU 槽位；其余由 CPU 用主机内存里的原始专家计算，GPU 那边读 bank 末尾全零的备用槽位，down 之后两边相加。每个专家只从内存读一遍，上传和 CPU 计算同时进行。
- 计算图：CPU 分支先于 GPU 分支展开，所以它的 split 先跑。规划算子在 CPU split 的开头发出上传，CPU 算其余未命中时 DMA 在跑；GPU split 在流上排在上传之后。每层仍是一次同步，和原来一样。CPU 的 `mul_mat_id` 遇到 id < 0 跳过并把输出清零。只对 32 个 token 以内的批次、DeepSeek V4 的 SwiGLU 专家生效。
- 结果（4.8 万上下文，已开 `0008`，`tools/eval/m2-cpu-miss.sh`，复用提示词缓存后生成 256 token）：

  | 上传比例 | 解码 tok/s | 命中率 | 对全部上传的 top-20 KL |
  |---|---|---|---|
  | 全部上传（M1） | 30.6 | 75.5% | — |
  | 1.0（走新路径但全部上传） | 30.2 | 75.5% | 0，输出逐位一致 |
  | 0.5 | 36.1 | 75.9% | 2.7e-4 |
  | 0.4 | 35.7 | 75.1% | 2.2e-4 |
  | 0.3 | 36.4 | 74.5% | 1.7e-4 |
  | 0.2 | 36.0 | 73.1% | 2.2e-4 |
  | 0（全交给 CPU） | 16.1 | 0% | 1.8e-4 |

  只上传一半，命中率不降：按热度挑出来的才进缓存，冷门专家不会把缓存冲掉。新提示词刚开始、缓存还在预热时，比例越高越快（0.5 时 35.1，0.2 时 33.2），所以默认 0.5。12.8 万上下文：30.9 → 36.2 tok/s，KL 2.6e-4。
- 没做的：槽位池扩大到约 1,650 个（GPU1 已经只剩约 1.2 GiB）、预填充后按提示词热度预热（M3）。

## 4. 组件 B：CED 感知预填充

### 语义（来自官方参考代码 `inference/model.py`）

- 参考实现对提示词也跑满 40 层。CED 不是一个单独的模式，而是体现在 KV 怎么共享上：
  - 第 20 层的 compressor 从自己的注意力输入（也就是第 19 层的输出）生成解码器共享的全局 KV（ratio 1）。
  - 第 20 层的 indexer 生成索引键和候选块。第 24、28、32、36 层用自己的 query 重新索引，其余解码器层直接复用第 20 层的 top-k。
- 解码器层只有滑动窗口 KV 用到各层自己的隐状态：每层有一个 128 位的环形缓冲。
- 模型卡上说的 SWA Bounded Replay（`n_win`）在公开代码和配置里都找不到。

### 精确版（和参考实现等价）

对一段长 P 的提示词：

- **第 0–19 层**：全部 token 都算。
- **第 20 层**：注意力之前的部分（`hc_pre`、norm、compressor、索引键、滑动窗口 KV）全部 token 都算；注意力和 MoE 只算第 21 层需要的那些 token。
- **第 L 层（21–38）**：只算最后 128 + (38 − L) × 127 个 token。每过一层滑动窗口，依赖往前延伸 127 个 token。
- **第 39 层**：只算最后一个 token。

解码器层的 MoE 计算总量约 2.4 万次（token × 层），和 P 无关；现在是 20 × P 次：

| 提示词长度 | 现在 | 精确版 | 节省 |
|---|---|---|---|
| 8k | 16.4 万 | 2.4 万 | 约 7 倍 |
| 32k | 65.5 万 | 2.4 万 | 约 27 倍 |

### 实现

- 在 `deepseek4.cpp:1333` 的层循环里，进入第 20 层以后，每层用 `ggml_get_rows` 把隐状态裁成这一层需要的 token 尾段，做法和循环末尾的 `inp_out_ids` 一样。
- KV 写入：第 20 层的全局 KV 和索引键对全部 token 写入；各层的滑动窗口 KV 只写尾段。要确认 `llama-kv-cache-dsv4` 允许同一个 ubatch 里各层写入的 token 范围不同。
- 一段提示词会被切成多个 ubatch，只有最后几个 ubatch 需要跑解码器层。前面的 ubatch 跑完第 20 层的注意力输入部分就结束。
- 验证：同一段提示词，比较“跑满 40 层”和“精确版”之后各位置的 logits，KLD 应在数值底线以内。

近似版（只对最后 `n_win` 个 token 跑解码器层，更早的滑动窗口 KV 视为缺失）计算量更小，但 `n_win` 的值和屏蔽规则都没有公开。先做精确版。

### 实际实现（2026-10-21，`mx-llama.cpp/0003`）

- 只跳过 FFN，不裁注意力。第 20–39 层的注意力仍对所有 token 计算，所以 KV 的写入完全不变。被跳过的 token 的 FFN 输出置零，它们之后各层的隐状态是错的，但只会进入没有后续 token 读取的滑动窗口 KV。
- `llama_context::decode` 在 batch 分配后，给每个 token 算出它最多需要算到第几层：从输出位置往前每 127 个位置少一层，序列末尾的 256 + 127 个位置保证算到第 38 层。计算图里用 `ggml_get_rows` 取出要算的行，算完用 `ggml_set_rows` 放回。
- 每次调用按自己的末尾规划。DSV4 的 cache 本来就不允许回退到窗口中间（`seq_pos_min` 返回 `pos_max`，回退只能靠检查点或深度为 `n_rs_seq` 的回退环），而检查点都落在调用边界上，所以拆成多次调用也是正确的，只是省得少一些。
- 验证：8k、16k 上下文对拍，KLD 0.00006 / 0.00004，top-1 一致率 99.8%。server 上 4.8 万 token 的提示词，预填充从 355 提到 887 tok/s，解码不变。
- 第二步（2026-10-23，`mx-llama.cpp/0005`）：nsys 剖析显示，只跳 FFN 时热缓存 41.8 s 里，第 20–39 层的注意力占 19.9 s（每层约 1.0 s）。现在这些层仍对所有 token 写 KV，但只对子集取出 Q 和掩码行做注意力，反向 RoPE 和输出投影也只算子集，结果放回全零张量。预填充降到 27.9 s，对拍 KLD 0.00004–0.00007，temperature 0 的输出和第一步一字不差。
- 剩下的可省项：末尾那段的解码器层专家上传约 7 s（被调度到 GPU0，用不上 GPU1 的专家缓存）；server 在提示词末尾附近建检查点，把提示词切成两次调用，末尾段被算了两遍。

## 5. 组件 C：Engram 异步预取和行缓存

### 现状（`deepseek41.cpp`）

- 两张表都是 MXFP4，每行 256 维、136 字节，以 mmap 映射，设了 `MADV_RANDOM`，不预读。
- 行号在 `set_input` 里由 CPU 算好（`:223-308`），每个 token 每张表读 48 行。之后在 CPU 上执行 `get_rows`（`:383`），每次缺页都同步读一个 4 KiB 页。读完以后转成 F32，拷到 GPU。
- 2048 个 token 要读约 19.7 万行，用时约 2.4 s，每次读约 195 µs。瓶颈在缺页延迟，不在 SSD 带宽。
- 页缓存里现在有约 41% 的表（40 GiB）。两张表的访问次数相同，驻留量却是 7 GiB 对 33 GiB，说明淘汰不均匀。

### 设计

1. **先做最简单的**：在算完行号之后调用已有的 `llama_prefetch_rows`（`MADV_WILLNEED`），并把这两张表加进 `can_prefetch`（`llama-model.cpp:2305`）。先测这一步有多少收益。
2. **提前算行号**：提示词一切分成 token，就算出整段的行号，不用等到每个 ubatch 才算。解码时，下一个 token 一采样出来就算它的行号。
3. **io_uring 异步读**：`O_DIRECT` 4 KiB 读，队列深度 ≥ 256，读进锁页暂存区。第 k 个 ubatch 计算时，就预读第 k+1 个的行。约 3% 的行跨页，要读两页。
4. **按行缓存**：开放寻址哈希（行号 → 位置），用 CLOCK 或 2 位频率计数淘汰，防止只出现一次的 n-gram 把缓存冲掉。16 GiB 能放约 1.26 亿行；按 4 KiB 页缓存的话，同样 16 GiB 只能覆盖约 400 万个随机行。用 `O_DIRECT` 读之后，对两张表 `fadvise(DONTNEED)`，不再占页缓存。
5. **传 MXFP4 原始行到 GPU，在 GPU 上反量化**：PCIe 传输量减到 F32 的约 1/7.5。
6. **退出时保存热行号列表**，下次启动时只预热这些行，不扫全表（FEATURES.md 记载，加载时预读全表反而更慢）。

### 实际实现（2026-10-23，`mx-llama.cpp/0004`）

- 合并了步骤 1 和 2：`llama_decode` 拿到整批后，就在调用线程里算出全部行号（跳过前 3 个要回看上一批的 token），按地址排序后分给 `ABYSS_ENGRAM_PREFETCH` 个后台线程，每 4,096 个区间检查一次是否该停，用 fork 已有的 `llama_prefetch`（合并相邻页后 `MADV_WILLNEED`）发出预读。
- 哈希从 `set_input` 抽成 `engram_hash_token`，计算图里的读取和预取共用一份。对拍和不含这个改动的编译完全一致。
- 效果：4.8 万 token 提示词，每次测试前把两张表清出页缓存。不预取 91.1 s，8 线程预取 54.3 s；关掉 Engram 时冷启动是 52.4 s，所以冷读的开销从约 39 s 降到约 2 s。热缓存时两者都是约 42 s。
- 冷读已经基本藏在计算后面，io_uring、按行缓存和传 MXFP4 原始行（步骤 3–5）暂缓。等页缓存容量不够、热行命中率成为问题时再做。

### I/O 预算

预填充 1,000 tok/s 需要每秒约 9.6 万次行读取。即使缓存全不命中，也只是 9.6 万次 4K 随机读、约 0.4 GB/s，约占 9100 PRO 能力的 5%。

## 6. 组件 D：补上 V4.1 稀疏索引器

- 现状：`deepseek4.cpp:1260` 对 V4.1 跳过了 `build_csa_lid_attention`，改用 `build_hca_attention`，对所有压缩 KV 做稠密注意力。`indexer_proj` 和 `q_b` 加载了但没用上。
- 影响：压缩行在 512 以内时，结果和参考实现的 top-512 一致；上下文更长时就不一致了。也就是第 20–39 层（ratio 1）超过约 512 个 token、第 2–19 层（ratio 2）超过约 1,024 个 token 之后。用户的智能体请求有 1.5–4 万个 token，都落在不一致的范围里。
- 做法：按参考代码补上第 20 层的 Full 模式（建索引键和候选块）、第 24/28/32/36 层的 Reindex 模式，以及其余层的 Reuse 模式。
- 验证：没有现成的参考 logits。可以先在 CPU 上用官方 PyTorch 代码只跑注意力部分，取几层做对拍。

### 实际实现（2026-10-24，`mx-llama.cpp/0006`）

- 索引键：KV 源层（2、8、14、20）从压缩器 RoPE 之前的 latent 算 `k_norm(wk(latent))`，在组的位置上做 RoPE，再做 FP4 量化再反量化（每 32 个一块，缩放 `2^ceil(log2(amax/6))`，和官方 `kernel.py` 的 `fp4_act_quant` 一样）。压缩比 2 的层写进已有的索引键 cache，第 20 层写进新增的 `kv_lidp`，两者的 cell 都和对应压缩档一一对应。
- 打分：索引源层（2、8、14、20、24、28、32、36）用 `wq_b(qr)` 加 RoPE 和 FP4 得到查询，`weights_proj(x)/sqrt(128·32)` 得到每头权重，复用 fork 已有的 `ggml_lightning_indexer` 算 `Σ_h relu(q_h·k)·w_h`，再 `ggml_top_k` 选 512。第 20 层先按每 8 个位置取块最大值、把每个查询最新的块钉住、保留 2,048 块，第 24–36 层只在这些块里选；块数不超过 2,048 时这一步省掉。
- 注意力：非索引源层沿用最近索引源的 top-k；top-k 用 fork 已有的 `build_top_k_mask` 变成掩码，传 `n_kv_max` 走收集版 FA。CED 子集之间用 host 端的行映射衔接。
- FP4 用现有算子拼出来；`ggml_round` 在恰好处于中点时向远离零的方向舍入，硬件是向偶数舍入，只在精确中点上不同。
- 单层对拍（2026-10-24，`tools/eval/dump-indexer.sh` + `indexer_oracle.py`）：`llama-abyss-dump`（`0007`）导出 4,027 token 提示词在第 2、20、24 层的索引器输入输出，oracle 照官方 `model.py` 用 GGUF 权重重算，分三种算法：全程 float32；fork 的算法（Q8_0 矩阵乘把激活按 32 个一组量化成 int8）；官方的算法（bf16 激活，按 32 个一组量化成 e4m3、缩放取 2 的幂后做 FP8 GEMM）。结果如下：

  | 层 | fork 对 int8 参照 | fork 对 float 参照 | 官方算法对 float 参照 | fork 对官方算法 |
  |---|---|---|---|---|
  | 2 | 99.99% | 99.16% | 98.67% | 98.63% |
  | 20 | 99.98% | 98.67% | 97.14% | 97.11% |
  | 24 | 99.98% | 98.85% | 97.40% | 97.36% |

  表里是 top-512 集合的平均重合率。fork 和自己的算法对得上，说明 RoPE/YaRN、FP4、权重缩放、可见性和 top-k 每一步都对；剩下的差别来自激活量化，而且比官方算法自己的量化差别还小，所以不需要写精确的 FP4 内核。索引键 99.99% 以上完全一致，不一致的都是恰好落在 FP4 中点上的单个元素；最后一个没填满的压缩组也有键，但还没有查询能看到它。官方算法这一栏用的是 GGUF 里重新量化成 Q8_0 的 `wq_b`，不是原始 FP8 权重。
- 解码时的注意力（2026-10-24，`mx-llama.cpp/0008`，`ABYSS_DSV41_DECODE_GATHER=1`）：解码剖析发现，`build_hca_attention` 每层每个 token 都把滑动窗口和整个压缩 KV 拼成一个张量（`concat_cont`，4.8 万上下文时每次约 40 µs、每 token 约 3 ms，随上下文增长），再由 flash attention 按 top-512 掩码挑行。单个查询时，现在先用 `get_rows` 取出 top-k 行和它们的掩码，再和滑动窗口拼接，补齐到 256 的倍数后走普通 flash attention。解码 4.8 万上下文 27.7 → 30.6 tok/s，12.8 万 23.9 → 30.9 tok/s。对拍：`llama-abyss-dump` 加了 `ABYSS_DUMP_GEN`，导出解码步的注意力输入输出，`tools/eval/decode_attn_oracle.py` 用 float64 重算。给定相同输入时，两条路径看到的是同一组 640 行，和 float64 的误差都约 5e-4（F16 舍入）；server 上 temperature 0 的 top-20 KL 约 0.003，来自编码器层舍入差别经 MoE 选专家放大，属于改动经过编码器层那一档底线。

## 6.5 多轮智能体（2026-10-25）

用户的负载是长上下文的智能体（Codex），每轮在上一轮的基础上追加回复、工具结果或追问。`tools/eval/agent-turns.sh` 模拟这种会话：首轮 4.8 万 token 的文档加两个工具，之后每轮约 1,500 token。

- 缓存复用正常：每轮只重算上一轮的生成加 4 个 token。生成的 token 经模板重新渲染后和生成时不完全一样，server 退回「Assistant」前缀处的检查点。
- 每轮预填充 5.5–7 s，而只有 1,100–1,600 个 token。nsys 抓一轮（1,610 token，7.0 s）：GPU0 从主机上传专家 145 GiB、5.4 s，两张卡的内核合计约 1.4 s。超过 32 个 token 的批次在第 22–39 层几乎用到全部 384 个专家，这些大批次的专家矩阵乘被调度到 GPU0，每层整批上传；超过 2,048 token 的轮次分两个 ubatch，要传两遍。页缓存热了以后时间不变，所以不是 Engram。
- 上传期间 CPU、GPU1 的链路和 GPU1 的专家缓存都闲着。下限是把这些专家从内存读一遍（约 121 GiB ÷ 44 GB/s ≈ 3 s），可以把大批次也按 M2 的思路分流：缓存命中的在 GPU1 上算，token 少的专家交给 CPU，其余上传到 GPU0，三路同时进行；再让一段提示词的解码器层只上传一遍。

**大批次分流（2026-10-25，`mx-llama.cpp/0014`，`ABYSS_MOE_BIG_SPLIT=1`）**：

- 每层一个 CPU 算子统计每个专家的 token 数，按 token 数从少到多把专家交给 CPU，直到 CPU 的预计时间追上其余专家的上传时间。GPU 那一路的这些条目为 -1（CUDA MMQ 补了 -1 的处理：跳过并把输出清零），上传回调只传其余专家，而且直接用规划算子在主机上的结果，不必从 GPU 读回 id。
- 第一版的 CPU 分支处理整块张量（全部 token × 6 个专家），只用到约 5% 的行，量化、SwiGLU、清零和 252 MB 输出的回传把收益全吃掉了，比不分流还慢。改成紧凑批次：只取出交给 CPU 的「token × 专家」（最多 1,024 行），在 GPU1 上取出这些 token，CPU 上按一行一个专家算，`set_rows` 写回后和 GPU0 的结果相加。合并固定在 GPU0，否则 GPU1 的计算缓冲区会大 3.7 GB。
- 顺带修了 fork 的一处问题（`0013`）：`ggml_backend_sched_reserve_size` 在切分前重置调度器，清掉了构建计算图时手动指定的后端，按错误的切分估算显存。
- 结果：2,048 token 一批 4.88 → 4.24 s，KLD 0.00046；多轮智能体之后每轮 5.7–7.2 → 4.6–5.6 s，首轮 30.6 → 27.9 s。nsys 显示 GPU0 的上传减半，但 CPU 要等 gate 那批传完才开始，而且和 DMA 共享 44 GB/s 的内存带宽；离「每层专家从内存读一遍」的下限还有约 30 ms/层。

**Codex 的实际请求**（生产 server，6 个请求）：预填充合计 76 s，生成 129 s。除了上面的固定开销，还发现两处缓存问题，`0012` 已修：

- 只有一个槽位。Codex 会发辅助请求（和主对话共享约 4,500 token 的系统提示和工具定义，只问一句），它把主对话挤出槽位。server 把主对话存进了内存缓存，但主对话回来时，槽位里的辅助请求和它仍有 94% 的前缀相同，server 只在保留比例低于一半时才去缓存里找，而且按保留比例挑选，长的条目反而吃亏。现在按能直接用上的 token 数比较，多出 256 个以上就换入；只用到一小部分的条目复制一份、原条目留着。
- 辅助请求自己也是从头算：系统提示末尾（用户消息开头）有检查点，但 server 要求检查点比分叉点早至少 128 个 token。这是给保存滑动窗口的检查点定的规则；DSV4 的检查点是那个位置的完整状态（`pos_min == pos_max`），在分叉点之前就能接着算。
- 效果（同一场景）：辅助请求 3,950 token 从全部重算 8.4 s 变成恢复检查点后只算 13 个、0.3 s；主对话下一轮从内存缓存换回，只算 216 个、2.2 s。

**末段一遍算完（2026-10-25，`mx-llama.cpp/0015`）**：

- 问题：CED 让每次 `llama_decode` 调用都按自己的末尾跑解码器层，凡是超过 32 个 token 的调用都要把第 22–39 层几乎全部专家从内存读一遍。server 为了建检查点，会在最后一条用户消息开头、末尾前 4 + n_ubatch 和末尾前 4 处拆调用。从生产日志看，Codex 的大多数轮次被拆成两次大调用（例如 1,772 + 866 + 4），比同样长度只有一次调用的轮次多花约 1.5–2 s；一次调用里末段跨两个 ubatch 时也要读两遍。
- 做法一（`ABYSS_CKPT_TAIL_MERGE=T`，生产用 2700）：最后 T 个 token 里不再按用户消息开头和末尾前 4 + n_ubatch 拆，只留末尾前 4 个 token 那次（它让下一轮能从助手前缀处接着算，而且 4 个 token 走小批次路径，很便宜）。会话的第一个检查点照旧（还没有检查点时不合并），Codex 的辅助请求靠它复用系统提示。代价是这两类检查点没了，只有改写最后一条用户消息、或在最后 2,700 个 token 里分叉时才用得上，这时退回上一轮的检查点多算这一轮。
- 做法二（`ABYSS_CED_ALIGN=1`）：一次调用的余数放进第一个 ubatch，最后一个 ubatch 是满的 2,048 个。原来余数在最后，最后一个 ubatch 常常只有几百个 token，第 20–32 层左右都要在前一个 ubatch 里再算一遍；现在前一个 ubatch 只剩第 20–22 层的少量 token。
- 做法三：CED 末尾的余量原来固定 256 个位置，是给 `n_rs_seq` 回退留的；没开 DSpark 时 `n_rs_seq` 是 0，DSV4 不能部分回退（`seq_rm` 直接拒绝），只能退到检查点。现在默认等于 `n_rs_seq`，`ABYSS_CED_MARGIN` 仍可覆盖。按规划公式逐个位置核对过，余量 0 时下一个 token 需要的滑动窗口状态都是完整的。
- 结果（`tools/eval/agent-turns.sh`，生产配置）：

  | 配置 | 首轮 4.8 万 token | 之后 5 轮（1,200–1,600 token） |
  |---|---:|---:|
  | 改动前 | 27.9 s | 4.6–5.6 s |
  | 末段不拆调用 | 25.3 s | 3.2–3.7 s |
  | + 末尾对齐 | 24.4 s | 3.2–3.7 s |
  | + 余量 0 | 24.0 s | 2.9–3.5 s |

- 对拍（`m2-cpu-miss.sh`，4.8 万 token，temperature 0 + top-20 logprob）：和改动前比，前 28 个 token 一致，之后分叉；一致部分的 top-20 KL 平均 5.0e-3（只合并）、8.2e-3（三项都开），换了 ubatch 切分，属于编码器那一档底线。只合并和三项都开之间是 1.3e-2，样本只有 31 个 token，所以又分项测了：末尾对齐对改动前用 `kl.sh`（6,000 token 一段，4 段）是 KLD 0.0092、top-1 95.4%，和只把 ubatch 从 2048 改成 1024 的 0.0090、96.0% 一样，属于换 ubatch 切分的正常差别；余量 0 对余量 256 在 server 上生成的 256 个 token 全部相同，top-20 KL 4.6e-4，在解码器层那一档以内。新提示词首次请求 26.0 → 21.9 s，解码不变。
- 短提示词（`tools/eval/prefill-sizes.sh`，关闭 prompt 缓存，每档 3 次取中位数）：604 token 2.68 → 2.59 s，2,324 token 5.57 → 3.69 s，4,277 token 8.80 → 4.34 s。604 token 比 Codex 那次测的 646 token（1.54 s）慢，是因为这里是真实文本，几乎每层的专家都用到，要把第 22–39 层的专家都读一遍。
- 边界扫描（直接用 token 数组构造提示词，调用长度除以 2,048 余 0、1、2、7–9、31–33、127–129、1000、2047，各 2 千、4 千、2 万左右）：全部正常，续写连贯；末尾对齐后，2,049 token 3.4 s、4,095 token 4.0 s，余数基本不再影响时间。

**解码的实际速度（2026-10-25，`tools/eval/decode_modes.sh`）**：

- Codex 的实际会话（上下文约 10 万）解码只有 30–31 tok/s，而 `m2-cpu-miss.sh` 测的是 4.8 万 36.1、12.8 万 36.2。差别在测法：那里的解码速度是同一个提示词第二次、一字不差的生成，专家缓存里正好是上一遍用过的专家；同一脚本里第一次生成只有 32–35 tok/s。Codex 那次短上下文 47–49 tok/s 也是同一段生成重复跑的。
- `decode_modes.sh` 模拟只追加的会话：首轮放文档和工具定义，之后每轮追加上一轮的回答和新问题，生成 256 个 token，轮换贪心或默认采样、流式或不流式。9.6 万上下文 27–31 tok/s，4.8 万 27–29 tok/s，四种方式没有差别，所以既不是流式、采样，也不是上下文长度。
- nsys（每 token 约 37 ms，两种上下文几乎一样）：GPU1 上传未命中专家 14.5 ms（约 20 个、360 MiB，26.5 GB/s），GPU1 内核 10.4 ms，GPU0 内核 4.2 ms，两卡都空闲 8 ms；GPU1 的上传和内核完全没有重叠。和上下文长度有关的内核（注意力、索引器打分、top-k、取行和拼接）9.6 万时合计只有约 2 ms，top-k 已经是基数选择。这组测试的命中率 65%，Codex 实际会话是 76%。
- 结论：解码卡在未命中专家上，每层先等上传和 CPU 算完再算 GPU 那部分，一层接一层串行。能改的方向：上传和同一层的命中专家、共享专家并行算；查清每层约 0.45 ms 的两卡空闲在等什么；再往上是 DSpark 和内存频率。

## 8. 风险与待确认

- **GPU 和 CPU 两路串行执行**：调度器按顺序执行各个子图，GPU 和 CPU 之间每次拷数据都要同步，两路很可能没法并行，收益会低于模拟值。（2026-10-24：每层的 GPU 计算和 CPU 计算仍是串行，但未命中的上传和 CPU 计算已经同时进行，见第 3 节。）
- **新加的输入张量可能不在计算图里**：CED 会让某些层在某个 ubatch 里没有 token，依赖它们的计算被整段丢掉，预先建好的输入张量就不会分配，`set_input` 往里写就会断言失败。`0010`、`0011` 修了两处（都只在特定提示词长度下触发，由 Codex 暴露）。以后新加输入都要处理这种情况。
- **GPU 链路降速**：2026-10-24 有一次开机 GPU1 只训练到 PCIe Gen4，上传慢一半，解码慢三成，重启后恢复。测速脚本会检查。
- **CPU 上的 MXFP4 是否重排过**：现在 CPU 侧专家在 `CUDA_Host` 缓冲区里，没有走 `CPU_REPACK`，可以直接拷进 bank。要确认改动以后它仍然不会被重排。
- **bank 用的是普通 MXFP4 内核**：bank 不在重排过的缓冲区里，解码走普通 MMVQ 内核，可能比整层常驻的层慢一些。
- **槽位池全在 GPU1 上**：`-ts 12/29` 让第 12 层以后都在 GPU1，GPU0 已经满了。
- **热度和任务类型有关**：目前的数据只来自一类智能体负载。
- **Bounded Replay 的 `n_win` 没有公开**：所以 B 组件先做精确版。
- **mx-llama.cpp 的 q8_1 缓存 bug**：要一直设 `GGML_CUDA_Q8_1_CACHE=0`，最好修掉后报给上游。
- **DSpark 不支持 V4.1**：投机解码的收益暂时拿不到。
